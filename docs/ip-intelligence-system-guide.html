Summary

The system gives every IP address the company sees a location and a proxy/VPN/bot verdict, keeps both current every day, and lets anyone look up any address, one or a thousand at a time.

  • Sources of addresses: the production tables raw.raw_tune_clicks (ad clicks) and unified.unified_session_summary (website sessions). They are only ever read.
  • Answers from: IP2Location DB11 and IP2Proxy PX12 (downloaded databases), FraudLogix decisions carried on tune clicks, ipinfo.io and ipwho.is (free APIs), and proxycheck.io (paid, $9.99 a month, 80,000 queries a day).
  • Kept in: nine Iceberg tables in ipintel_curated, the main one being ip_resolved, one row per address with the answer to use.
  • Kept current by: a daily load at 07:30 UTC for new addresses, a proxycheck.io run straight after (new-row addresses first, then the backfill, together up to 50,000; 30,000 a day stay free for API lookups), a 22:00 UTC top-up that finishes the 50,000 if the morning run stopped early, and weekly maintenance.
  • Shared with another team: after every proxycheck.io run that passes its checks, unified.ip_geo and unified.ip_intelligence are refreshed with checked copies of the ipintel_curated tables (files only, no catalog change).
  • Reported by: a Location Accuracy report (vendors against customer postal addresses) and an Enrichment Coverage report, rebuilt at the end of both daily jobs.
  • Used through: a Lovable app, an HTTPS API (GET /lookup/{ip}, POST /lookup for up to 1,000, table and control endpoints), and Athena.
  • Safety: every project role sits inside a permissions boundary that makes writing to any production table, bucket or workgroup impossible; every run proves it and reviews its own AWS activity.

The daily cycle

Job A — the incremental load (07:30 UTC)

  1. Stops if the pipeline is paused or the job is switched off (a manual run ignores the switch).
  2. Removes staging tables older than 3 hours left by any crashed run.
  3. Asks the IAM simulator whether its role could write to production. Any "yes" fails the run and pauses the pipeline.
  4. Takes the enabled, validated base tables and records the latest Iceberg snapshot of each. If none changed since the last successful run, it stops ("skipped").
  5. New addresses: every valid IPv4 in any base table, at the pinned snapshot, that IP2Location has not answered yet. A full comparison is used, so rows that arrive late or are rewritten are never missed.
  6. FraudLogix targets: new addresses plus addresses with clicks in the last 3 days, because a FraudLogix decision can change.
  7. Looks up IP2Location DB11 and IP2Proxy PX12 (range joins on the downloaded databases) and FraudLogix (latest decision per address from tune clicks).
  8. Asks ipinfo.io and ipwho.is about addresses new since 14 Sep that they have not answered, up to 500 each per run, paced.
  9. Counts what will change (inserted / added / updated / unchanged), then MERGEs into ip_geo and ip_intelligence. created_at is never overwritten.
  10. Refreshes ip_intelligence_analytics and ip_geo_analytics for the affected addresses.
  11. Recomputes ip_occurrences from every base table and merges it (first seen only moves earlier, last seen only later).
  12. Recalculates both vendor scorecards over addresses asked of every running vendor (at least 1,000) and exports them for the app.
  13. Recomputes ip_resolved for every address and merges only rows that changed.
  14. Queue: every address new or touched since the last successful run that needs proxycheck.io goes into proxycheck_queue with its reason.
  15. Rebuilds the Location Accuracy and Enrichment Coverage reports (reports).
  16. Runs the checks below and a CloudTrail review. If any fails, progress is not recorded, so the next run repeats the same work.
  17. Records each base table's new snapshot as its watermark and starts Job B.

Job A checks: pipeline cannot write to production · no address twice for a vendor · no table shrank · every new address is in ip_geo · IP2Location has every new address · IP2Proxy has every new address · updated geo rows kept created_at · updated intelligence rows kept created_at · every address has exactly one resolved answer · every new address has an occurrence row · every address needing proxycheck.io is queued · location accuracy per vendor exported · enrichment coverage exported · nothing outside the project was touched in 24 hours.

Job B — proxycheck.io (after Job A; 10:00 fallback; 22:00 top-up)

  1. Same pause, switch and permission checks. Reads the key from Secrets Manager and proxycheck.io's own usage page (plan, limit, queries used).
  2. Plans the day once: picks up to 50,000 × 99% addresses without a proxycheck.io answer (job_proxycheck._selection_sql), in this order:
    • 0 queued from base tables;
    • 1 first seen today;
    • 1b (new, 15 Sep) every address seen in the base tables in the last 30 days that proxycheck.io has not answered, even if the other vendors agree it is clean, because proxycheck.io confirms the proxy answer and adds a second location vote;
    • 2 no conclusion (no_answer, vendors_disagree, flagged_unconfirmed), seen in the last 90 days first, then by class rank and most recently seen.
    Private and reserved addresses are never picked. Saves the list as batch files of 1,000 and a manifest.
  3. Queue batches: on every run, queued addresses not in today's batches become extra batches sent first, so addresses queued after the plan still go out the same day. They count inside the 50,000 (queue_extra 0) and never borrow from the lookup reserve.
  4. Top-up batches (22:00 run only): the next addresses in the same order, sized to what is left of today's 80,000 minus 30,000 (topup_keep), judged by the larger of our counter and proxycheck.io's. In practice it only finishes the 50,000 enrichment budget when the morning run stopped early; it never uses lookup queries.
  5. For each batch without a saved response: reserve its queries atomically, send 1,000 addresses in one request, save the response file immediately, then account for addresses charged twice.
  6. With under 3 minutes left, or under 10 minutes when the merge is still to do, it starts a fresh copy of itself and stops (at most 30 hand-overs a day; a failed hand-over lands in the dead-letter queue with an alarm).
  7. Merges every saved response not yet applied, plus every answer saved by API lookups in the last 7 days, into ip_intelligence and ip_geo; refreshes analytics, scorecards, exports and ip_resolved. Writes an "applied" marker per file only if every check passes.
  8. Closes queue rows whose answer is now in the tables (or that proxycheck.io had no record for), rebuilds the two reports, then runs its checks and the CloudTrail review.
  9. Publish: only when every check passed and publish_unified is true on job/proxycheck-daily, invokes itself with {"action":"publish"} to refresh unified.ip_geo and unified.ip_intelligence (below).

Job B checks: pipeline cannot write to production · no duplicates · no table shrank · created_at kept (geo and intelligence) · one resolved answer per address · every queued base-table address was sent · location accuracy per vendor exported · enrichment coverage exported · nothing outside the project touched.

16 Sep plan (dry run of the new order): 49,504 addresses selected. The first 20,597 are every remaining address seen in the last 30 days (8,719 no_answer and 11,878 clean_by_vendors); the other 28,907 are older no_answer addresses last seen 31–90 days ago. After the 16 Sep run, every address seen in the last 30 days has a proxycheck.io answer, except those proxycheck.io has no record of.

When proxycheck.io is asked

One rule, written twice in the same order: lookup.needs_proxycheck in the API and pcqueue.reason_sql in the pipeline.

  1. Not a public address (0/8, 10/8, 100.64/10, 127/8, 169.254/16, 172.16/12, 192.0.0/24, 192.0.2/24, 192.168/16, 198.18/15, 198.51.100/24, 203.0.113/24, 224/3) → never.
  2. Refresh requested (API only) → yes, refresh.
  3. proxycheck.io has already answered → no.
  4. Not in the IP tables → yes, new_address.
  5. No location → yes, no_location.
  6. Proxy status no_answer, vendors_disagree or flagged_unconfirmed → yes, that status.
  7. Location vendors disagree → yes, location_disagree.
  8. Otherwise → no.

Tested 15 Sep: 9 of 9 offline cases; through the live API 4 of 4 should-call cases called, 3 of 3 must-not cases not called, 2 of 2 repeats not charged again; bulk endpoint the same.

How the answer is resolved

Vendor rows are never changed to make them agree. The answer to use is worked out from them by fixed rules, identically in resolved.py (SQL, for ip_resolved) and lookup.py (Python, for lookups). A comparison of 1,000 addresses found 0 differences.

Location

  • A vendor "answered" if it gave a state, a city or coordinates. GeoJS never votes (it repeats MaxMind); it is also no longer running.
  • Answers are grouped by lower-cased state and the first word of the city.
  • The group with the most vendors wins; ties go to the group holding the best location-scorecard score, then to the group whose first vendor id sorts first.
  • The best-scoring vendor in the winning group supplies every field.
  • Status: agreed if the group has 2+ vendors; single_source if only one vendor votes; otherwise vendors_disagree.

Proxy

  • A vendor "answered" if is_proxy is not empty. It is "flagged" if any of proxy, VPN, Tor, datacenter, bot, compromised, scraper is true.
  • If proxycheck.io answered, its flags are used: confirmed when another answering vendor has the same flagged/clean verdict, proxycheck_only when no other vendor answered, proxycheck_overrides when all others disagree.
  • Without proxycheck.io: clean_by_vendors when every answering vendor says clean (all flags false); vendors_disagree when some flag and some do not; confirmed_by_published_range when all flag and a published range agrees (no range data is loaded now); otherwise flagged_unconfirmed. No answers at all is no_answer.
  • ISP and ASN come from proxycheck.io when present, otherwise the first answering vendor by id.

Refreshing the unified tables

After every Job B run that passes all its checks, Job B replaces the files behind unified.ip_geo and unified.ip_intelligence with a checked copy of the matching ipintel_curated table. It never changes the Glue catalog.

Another team's API, ip-lookup-api, reads these two tables. They are Hive tables, Parquet, bucketed into 64 by ip_address, with files in the project's own folder s3://datalake-landingzone-221490242148-us-west-2/ip-intelligence/unified/table/d=2026-09-11/. Because the files are ours, the refresh can swap them without any catalog write. Code: build/pipeline/src/publish.py. Switch: publish_unified on job/proxycheck-daily (true).

Steps, per table

  1. Guard. The unified table still has the expected S3 location, exactly the same columns as ipintel_curated.table, 64 buckets on ip_address, and Parquet. Anything else stops the publish.
  2. Archive (first publish only). Copy the 11 Sep files to ip-intelligence/archive/unified-2026-09-11/table/, kept forever.
  3. Build. CTAS a bucketed Parquet copy of ipintel_curated.table into staging.
  4. Check the copy. Same row count as the source; no duplicate (ip_address, vendor); 64 bucket files; about 200 sample addresses (the newest per vendor plus random ones) return identical rows through the bucketed lookup path.
  5. Swap. Copy the current files to ip-intelligence/publish-previous/table/ (the rollback copy), copy the new files in, then delete the old ones. For a few seconds readers may see old and new rows together; they never see an empty table.
  6. Re-check. Run the same checks on unified.table. On any failure, the previous files are put back automatically.

Code build/pipeline/src/accuracy.py; file geo_accuracy.json; API GET /accuracy/geo; check "Location accuracy per vendor exported".

FraudLogix mapping

Latest decision per address. Not FLAGGED → every flag false, reason ACCEPTED. FLAGGED with reason PROXY or MOBILE_PROXY_SIGNALS → proxy; VPN → VPN; TOR or TOR_EXIT_NODE → Tor; DATA_CENTER → datacenter; BOT_GENERATED or NON_HUMAN_SCRIPT → bot; MASKED_DEVICES → no flag, is_masked_device true (a device fingerprint signal, not a bot signal). Clicks with no decision → no answer.

proxycheck.io mapping

proxy: yes → proxy; vpn: yes → VPN; type Tor → Tor; type Hosting → datacenter; type Compromised Server → compromised; type Scraper → scraper; operator anonymity, proxy or VPN → anonymous; bot is always empty. Business is not datacenter: in a test of 400 real addresses, 112 were Business, mostly Charter, Cox, AT&T, CenturyLink and Verizon Business home and office broadband. last seen unix becomes updated_at.

Production safety

The pipeline cannot harm production because AWS will not let it, and every run proves that before it starts.

The fence

Every project role has the permissions boundary ipintel-boundary. Whatever a role's own policy says, the boundary explicitly denies:

  • any Glue write outside ipintel_curated;
  • any S3 write outside datalake-landingzone-221490242148-us-west-2/ip-intelligence/*, and every bucket-settings change;
  • queries in any Athena workgroup other than ipintel and ipintel_etl;
  • any Lambda outside ipintel-*;
  • loosening the boundary itself, and deleting the project's own safety resources.
RoleUsed byProof
ipintel-builder-roleEvery build step (profile ipintel-builder)IAM simulator 61 / 61 refusals
ipintel-pipeline-roleBoth jobsIAM simulator 64 / 64 refusals; re-checked at the start of every run
ipintel-api-roleThe APIHardened: its old write access to every unified table was removed
ipintel-scheduler-roleSchedulesCan only start the two job functions

Every run

  • Before: the IAM simulator is asked whether the pipeline role could update or delete the production tables, write their buckets, change bucket notifications or lifecycle, or query in primary. Any "allowed" fails the run and pauses everything.
  • After: CloudTrail is read for every call the job functions made in 24 hours; any write aimed outside the project is a failed check and an automatic pause.

Publishing to the unified tables

The refresh of unified.ip_geo and unified.ip_intelligence stays inside the fence. It only copies and deletes files under ip-intelligence/ (the tables' own files, staging, the rollback copy and the archive), which the boundary already allows. It makes no Glue change at all: ipintel-boundary denies Glue writes in the unified database, and the builder role cannot loosen the boundary. The before-run IAM simulator check and the after-run CloudTrail review are unchanged, and publish runs only after both have passed for that Job B run.

They were reported to the owner and are unrelated to this project. Also noted: the BounceEvents EventBridge rule matches every S3 write in the account but has no target today.

Runbooks

A job failed

Read the run's message and checks on Daily Jobs (or GET /jobs/{id}/runs). Nothing half-done is recorded as done. Fix the cause, then Run now. Answers already saved to S3 are merged on the next run.

A safety check failed and the pipeline paused itself

Do not resume. Compare the role and boundary policies with the copies in build/iam/; find what granted access; restore; run the job by hand to re-check; then resume with a reason.

The key was rejected

Renew the plan or put the new key in ipintel/proxycheck-paid (Secrets Manager, us-west-2). Run the proxycheck job by hand; the budget page should show "Key working".

Something in the dead-letter queue

A hand-over did not start. Run the proxycheck job by hand; it continues from the saved batches. Then clear the message from the queue.

Switch the table pages back to the unified copy

Set mode to shadow on the safety/state item. The API picks it up within a minute. Nothing else changes.

Check the last publish of the unified tables

Call GET /publish, or read the Unified tables card on Daily Jobs, or read DynamoDB publish/unified and the newest run#publish-unified item. last_published_at should be after today's Job B run; each table lists its row count and checks.

Roll back a publish

Copy the files in ip-intelligence/publish-previous/table/ back into ip-intelligence/unified/table/d=2026-09-11/, then delete every other file in that live folder. To go back to the original copy instead, use ip-intelligence/archive/unified-2026-09-11/table/. Use the ipintel-builder profile. Stop publishing first (below), or the next passed Job B run replaces the files again.

Stop publishing

Set publish_unified to false on the job/proxycheck-daily item. Job B keeps running; the unified tables keep their last copy.

Dry-run a publish

Invoke ipintel-proxycheck-daily with {"action":"publish","dry_run":true}. It builds and checks the copies without swapping, and logs the run under run#publish-unified.

A report is missing or stale

The app shows "appears after the next daily run" until the file exists. Check the "Location accuracy per vendor exported" and "Enrichment coverage exported" checks on the last run, then Run now on either job.

Undo a data correction

Removed benchmark rows: archive/benchmark-vendors-2026-09-14/ (JSON). FraudLogix timestamps before conversion: archive/fraudlogix-timestamps-before-utc-2026-09-15/ (Parquet). Recent table versions can also be read with Iceberg time travel for 5 days (maintenance removes older ones).

Add a vendor back as a real source

Load its database into ipintel_curated under the table name in vendors.OPTIONAL_*_DATABASES, switch it on in the registry, and the daily job starts asking it about new addresses and scoring it.

Pipeline: zip build/pipeline/src/*.py (common, vendors, apply, resolved, pcqueue, accuracy, coverage, publish, job_free, job_proxycheck) and update both job functions. API: zip build/api/src/*.py (app, athena_tables, bulk, control, lookup) and update ipintel-findings-api. Always with the ipintel-builder profile, never the default profile.

Glossary

Iceberg
A table format in S3 that allows safe updates (MERGE), versions (snapshots) and time travel. Readers always see a complete version.
MERGE
One SQL statement that updates matching rows and inserts new ones: the "append if it exists, insert if it doesn't" of the requirements.
snapshot / watermark
A table version. Job A records the snapshot it read from each base table, so the next run knows what changed.
staging table
A short-lived working table for one run, removed afterwards.
permissions boundary
An AWS ceiling on what a role can ever do, whatever its own policy grants.
IAM simulator
An AWS service that answers "would this role be allowed to do this?" without doing it.
CloudTrail
AWS's log of every API call made in the account.
hand-over
A Lambda run starting a fresh copy of itself to continue, before its 15-minute limit.
dead-letter queue
Where a failed asynchronous start is kept so it is not lost.
reservation counter
The DynamoDB item every proxycheck.io request reserves from first, so two callers can never both take the last queries.
resolved answer
The one answer to use per address, from fixed rules over every vendor's answer.
no conclusion
No vendor answered, vendors disagree, or a flag has nothing confirming it.
agreement
How often a vendor matches the other vendors; the vendor overview scorecards measure agreement.
accuracy
How often a vendor's location matches customer postal addresses (qualified_lead_ips). Used only on the Location Accuracy report.
enrichment
proxycheck.io queries spent on base-table addresses (queue, backfill, top-up), up to 50,000 a day; the other 30,000 are kept for lookups.
enrichment coverage
How many addresses have a proxycheck.io answer, a proxy conclusion and an agreed location; the Enrichment Coverage report.
publish
Job B's refresh of unified.ip_geo and unified.ip_intelligence: build a checked bucketed copy, swap the files, re-check, restore on failure. No catalog change.
rollback copy
ip-intelligence/publish-previous/table/: the files the last publish replaced.
confirmed human
An address a qualified customer lead used (qualified_lead_ips.confirmed_human); a bot flag on it is a false positive.
mode
live: table pages read ipintel_curated; shadow: they read the unified copies.
Kept in the project folder as docs/ip-intelligence-system-guide.html. Companion: IP Intelligence User Manual. Evidence: IP_PROJECT_VERIFICATION.md.
