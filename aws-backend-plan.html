Recovered

But the truth table is contaminated

proxy_sessions and vpn_sessions come from ip_is_proxy / ip_is_vpn on the session table — which are already some vendor's opinion, carried in by the existing pipeline. They are sitting in a table called business truth.

That breaks the product's own rule: never treat one vendor as ground truth for another. Score a vendor's proxy detection against these columns and you are measuring agreement with an unnamed incumbent, not accuracy. Business truth is sessions, leads, verified leads and revenue — things that actually happened. Proxy and VPN claims belong in ip_vendor_result under whatever source produced them, and that source needs identifying before P1 writes anything.

The ip_flags CTAS in athena_tables_fixes.txt failed with COLUMN_NOT_FOUND: 'created_at'. That column does not exist on raw.raw_tune_clicks — the real ones are datetime and date_pst. Substituting those makes the script run as written.

The measurement rules already learned the hard way

These are worth encoding once, centrally, because each produced a confidently wrong dashboard:

  • Missing means three things. IP2Location writes '-', the session table writes NULL, and exports write ''. One shared expression — nullif(nullif(x,''),'-') — everywhere, or fill rates read 100% when they are 99.83%.
  • Absence from PX12 is not a clean verdict. DB11 covers all 4.29B IPv4 addresses; PX12 is a sparse list of known proxy ranges. A miss means unknown, never clean. This is a schema-level distinction (has_answer), not a query-level one.
  • A null join result is not a measurement. ip_analytics is the cautionary case: it ran, it succeeded, it wrote 1.99M rows, and every vendor column was null. Coverage assertions have to run inside the job — a row count alone would have passed this.

One view is a landmine

v_ip_intelligence joins db11_parquet to px12_parquet on overlapping ranges — p.ip_from <= d.ip_to AND p.ip_to >= d.ip_from — with no bucketing key. That is a range join across 2.98M × 2.69M rows with nothing to partition on. It will either run for a very long time or fail expensively, and it duplicates rows wherever ranges overlap partially. The prefix16 bucketing technique already proven in the profiling work exists precisely to avoid this. The view should be dropped rather than fixed, because the tall table replaces it.

The non-obvious call

Athena is not allowed on the request path. A dashboard query returns in two to twenty seconds and bills per terabyte scanned; a Cloudflare Worker has a hard CPU budget and the user has a two-second patience budget. If the API queries Athena live, every screen feels broken and every page refresh costs money.

So Athena runs on a schedule and writes small, already-aggregated results; those get loaded into Postgres; the API reads Postgres and answers in milliseconds. Athena appears on the request path in exactly one place — an explicitly asynchronous "deep dive" that returns a job id, never a rendered screen.

Why RDS is in the picture at all

The architecture doc already calls for it, and it is genuinely needed regardless of serving strategy: jobs, tasks, vendor registry, plan limits and usage counters are transactional, small, and updated by users — none of that belongs in a data lake. Once Postgres exists for that, using it for the serving tables too is the smallest system that works. A single db.t4g.small handles both; ip_dim at ~5M rows with a b-tree on the IP is a couple of gigabytes and answers IP Explorer point lookups instantly.

The four rules that make the layout hold

  1. Every table declares its own location. Every CTAS carries external_location = 's3://…/processed/<table>/…'. No exceptions, so Athena never picks a path again.
  2. Snapshot date is the rollback mechanism. A bad DB11 load writes a new snapshot_date partition; the previous one is untouched. Rolling back is repointing the current-snapshot view, not restoring from backup.
  3. Raw is append-only and never reshaped. If a normalization rule turns out to be wrong, it is rerun from raw. This is the only thing that makes vendor comparisons defensible six months later.
  4. Query output lives outside the data. athena-results/ has a lifecycle rule and is not addressable by any table — which is exactly the failure that exists today.

Catalog

Keeping ip-database means quoting it in every statement forever, and it currently mixes reference data, curated tables, analytics and six empty shells. Three databases — ipintel_reference, ipintel_curated, ipintel_analytics — separate the layers and drop the hyphen. The existing warehouse databases raw (TUNE clicks) and unified (sessions) are read, never written. The empty tables and the seven views in ip-database get dropped once their replacements pass P1's gate, not before — a broken table that still describes its columns is the only remaining documentation of what was intended.

Structural guardrail — confirmed necessary

I checked the primary workgroup this runs under: OutputLocation is null, EnforceWorkGroupConfiguration is false, and there is no bytes-scanned cutoff. That is the whole mechanism by which CTAS output ended up in Unsaved/ — nothing in the account prevented it, and nothing prevents it happening again tomorrow.

So: a dedicated ipintel workgroup with output pinned to athena-results/, client-side settings override enforced, and a per-query scan cutoff. Enforcement is what makes the failure impossible rather than merely discouraged, and the cutoff kills a runaway range join — like the one in v_ip_intelligence — before it bills.

Adding Spur, or MaxMind, or a vendor that does not exist yet, must be rows and configuration — never a migration.

Everything hangs off one tall table. One row per IP per source, with the union of what any source can say. A source that has no opinion on geography leaves those columns null; it does not get its own table or its own column.

Around it sit three small tables: vendor_product (the registry the Sources and Costs screens read — company, product, delivery, purpose, owner), vendor_plan (limits and cost model, driving CPM and plan-impact math), and ip_business_outcome (sessions, leads, verified leads, revenue, customers, refunds, per IP per day — the ground truth that makes false-positive revenue computable at all).

Normalization is data, not code

The mapping from a vendor's native verdict to the canonical vocabulary — residential_proxy · datacenter · vpn · tor · bot · crawler · clean · unknown — has to run in two very different places: Athena SQL for five million rows, and Python for a live API lookup. Written twice, it drifts, and the two halves of the console disagree.

So it lives in ctl/vendor_verdict_map/ as rows: (vendor_product_id, source_field, raw_value, risk_category, default_confidence). Batch SQL joins to it. The Lambda reads it. Adding a vendor's vocabulary is an insert, which is the same rule as adding the vendor.

Fail loud, not clean

An unmapped verdict resolves to unknown and is written to a daily unmapped-values report. It must never fall through to clean — that is how a proxy silently becomes a customer. The FraudLogix reason codes already include undocumented numeric values ("10" at 82,092 IPs, "9", "8") that no one has yet interpreted; they will hit this path on day one.

ProxyCheck, and what 1,000 lookups a day buys

The third source is live and tested. Its daily limit is not a limitation so much as the reason the Jobs screen exists.

The free key works, including batch POST (up to 100 IPs per request, each IP counted separately against the quota). One response carries a proxy verdict, a risk score, full geolocation, ASN, operator detail and device counts — so ProxyCheck is a geo source and a risk source and a shared-infrastructure signal, all three, and it registers as one vendor product with all three capability flags set.

The quota reframes the roadmap

The free tier is 1,000 lookups a day. The console's mock data claims an 80K/day ProxyCheck plan; that number is fiction and every figure derived from it is too. At 1,000/day, enriching all 4.9M IPs takes thirteen years, and even the 16,771 IPs that PX12 covers takes seventeen days.

So ProxyCheck is never a bulk enrichment source. It is a sampling instrument, and the daily budget gets spent on the IPs where the answer is worth the most: highest revenue at stake, flagged by FraudLogix, no corroboration. That is exactly what the Jobs & Sampling screen was designed to do — the constraint makes the feature necessary rather than decorative. A daily scheduled sampler that spends precisely 1,000 lookups on the top of that queue builds a defensible comparison set of ~30,000 adjudicated IPs a month, which is more than enough to rank three vendors.

Practically: the key goes into Secrets Manager as ipintel/proxycheck and is read at call time by the worker Lambda. It should not be in a repo, a Lovable env var, or a browser bundle — and since it has been pasted into chat, rotate it in the ProxyCheck dashboard once the secret is in place.

Authentication

The only client is Lovable's server, never a browser. So the API uses IAM auth with SigV4, signed inside createServerFn with credentials held in Lovable's secret store. No API key is ever shipped to the client bundle, and a leaked page source exposes nothing. Per-user identity and roles come later, in the app's own auth layer, forwarded as a signed claim the API checks against a user_roles table — never a role column on a profile.

07

How the UI work gets unblocked immediately

The frontend does not wait for AWS. It waits for the response shapes — and those can be frozen this week.

The console today reads every figure from src/lib/console-data.ts. The migration is not a rewrite; it is inserting one seam:

  1. Freeze the contract. Write the per-screen response types once, derived from the existing src/lib/types.ts, and publish them as OpenAPI. Both sides generate from it, so a shape change is a compile error rather than a runtime surprise.
  2. Add a server function per screen under src/lib/*.functions.ts. On day one every handler returns the matching console-data.ts constant. The screens now consume an async contract while still rendering exactly what they render now.
  3. Convert routes to loader + useSuspenseQuery, per the repo's own stated pattern. Still no backend involved. This is where loading and empty states get built — the work that is otherwise discovered late and rushed.
  4. Flip one env var per screen. When /kpi/overview goes live, the Overview handler proxies to AWS; the other ten keep serving fixtures. Screens go live independently, and every one of them can be reverted in a deploy.

The practical effect: filter-bar state, the disagreement-queue interactions, the drawers, the job form, loading and error states — all of that is real frontend work that can proceed in parallel with P0–P2 below, against fixtures, with zero rework when the data arrives.

09

Getting to the prompting phase

The question is what has to be true before Cursor or Lovable can be pointed at this and produce something that works. The answer is smaller than it looks.

A coding agent cannot invent the shape of your data, and it will confidently hallucinate one if you do not give it the real thing. Everything below is about producing the three artifacts that make the prompting phase deterministic instead of a negotiation.

What has to exist first

  1. The workgroup and the databases — half a day. Without enforcement, the next agent-run CTAS lands in Unsaved/ exactly like the last five did, and this audit gets repeated in a month.
  2. One rebuilt end-to-end table — ip_vendor_result populated for DB11, PX12 and FraudLogix, with the enrichment join actually landing. This is P1 and it is the real work. Until it exists there is nothing for a backend to serve.
  3. The OpenAPI contract — generated from the tables, not from the mock. This is the single artifact that unblocks every downstream prompt.

Then the prompting phase splits in two

TrackToolGivenProduces
BackendCursor, on a new repoOpenAPI spec · the table DDL · the verdict mapCDK or SAM stack, read Lambdas, the SQS sampler, tests
FrontendLovable, on the existing projectThe same OpenAPI spec · generated TS typesServer functions per screen, wired to the contract

Both tracks consume the same spec, which is what keeps them from drifting. Lovable never learns an AWS detail; Cursor never learns a component name.

Do this in Lovable before AWS is ready

Ask it for one change only: replace every direct console-data.ts import with an async server function that returns the same constant, and convert each route to loader + useSuspenseQuery. No visual change, no new data. It is a mechanical refactor that Lovable does well, and it is the seam every later prompt depends on. Do it now and the eventual cutover is one handler body per screen; skip it and you are asking an agent to restructure data flow and integrate an API in the same prompt, which is where these projects break.

Download the codebase, then keep Lovable

Your step 4 — export to Cursor — is right for the backend and worth being careful about for the frontend. The repo has hard constraints an agent will violate by default: no react-router-dom, never edit routeTree.gen.ts, no tailwind.config.js under Tailwind v4, no hardcoded colours, no duplicate Vite plugins. PROJECT_CONTEXT.md §10 already lists them. That file, or a CLAUDE.md/.cursorrules derived from it, has to be in the repo root before the first prompt, or the first refactor quietly breaks the build.

Keep the UI work in Lovable for as long as the changes are UI changes — it knows its own conventions. Move to Cursor for the AWS stack and the contract plumbing, where Lovable has no advantage.

One correction to the sequence you sketched

Your step 3 is "make the UI as per brand guidelines" — that is already done, and the Lovable console is considerably further along than the preview.html and index.html prototypes. Those two are not a design target any more; the eleven-route console is. The only reason to open the prototypes again is Bill's original intent for a screen the console does not yet cover.

10

Access

Not a blocker. If anything, the opposite problem.

The source-creation-tool profile resolves to arn:aws:iam::221490242148:user/source_creation_tool_user — underscores, not hyphens, which matters when writing policies against it. I simulated the actions this build needs and every one came back allowed: bucket and lifecycle management, Glue database and table creation, Athena workgroup administration, Lambda, API Gateway, SQS, EventBridge, RDS, Secrets Manager, CloudFormation, and iam:CreateRole / iam:PassRole.

That reach comes from group membership — data_platform, app_team, data_science — and includes IAMFullAccess and AmazonAthenaFullAccess. The user's own inline policies are narrow and belong to other projects entirely (csv_upload/, a Lovable backup prefix, a PitchPrfct repair grant).

Worth raising, not worth blocking on

Building a data platform from a human user that carries IAMFullAccess means every resource is created by a principal that could also rewrite its own permissions, and nothing distinguishes this project's footprint from anything else those groups touch. The cleaner arrangement is a dedicated IpIntelDeployRole scoped to the ip-intelligence/ prefix and ipintel-* resources, which source_creation_tool_user assumes — the same pattern already used for SourcesRawWriterRole. It costs about an hour in P0 and makes the blast radius legible.

11

Open questions

Ordered by how much they block. The first three change the plan; the rest change the details.

01

What produces ip_is_proxy and ip_is_vpn on the session table?

Blocking for every accuracy metric. These columns are already in ip_business_truth as proxy_sessions / vpn_sessions, so an unnamed vendor is currently sitting inside the truth table. Until the source is identified it becomes its own row in ip_vendor_result and comes out of business truth — scoring vendors against it would measure agreement with the incumbent, not accuracy.

02

How should revenue on shared infrastructure be counted? Cloudflare, Fastly and CGNAT addresses dominate the top of the revenue ranking.

It changes the product's headline metric, not just a chart. Options are to exclude shared infrastructure from false-positive revenue, to report it as a separate band, or to attribute at a coarser grain than IP. Deciding after the numbers are published is much worse than deciding now.

03

Do MaxMind and Spur credentials exist? ProxyCheck is answered — the free key is live and tested.

With ProxyCheck in hand there are three comparable sources, which is enough to make Compare and Bot & Proxy real. MaxMind and Spur decide whether it becomes five. Lower priority than it was yesterday, but it still shapes the Sources and Costs screens, which currently list vendors we cannot call.

04

What is the monthly AWS budget?

It picks the serving layer. A always-on Postgres is roughly $25–45/month; if that is unwelcome, the serving layer becomes DynamoDB and the design shifts before anything is built, not after.

05

Metro and county — where do they come from? No vendor in the current set supplies them, but four screens display accuracy at those levels.

Needs a ZIP→CBSA/county crosswalk as a reference dataset, or those rows come out of the accuracy tables.

06

IPv6. Every regex and integer conversion in the existing work is IPv4-only, so IPv6 traffic is currently invisible rather than counted as uncovered.

Either a stated out-of-scope decision with an explicit "IPv6 excluded" count on the coverage screens, or a second pipeline. Silence is the one option that produces wrong numbers.

07

Is IP masking presentational or structural? The UI shows 73.***.***.21.

If IPs are treated as personal data, masking has to happen in the API and full IPs need a separate authorization path — which affects the schema, not just the component.

08

Renew or retire the IP2Location Historical Commercial DB?

It is the difference between historical location accuracy being measurable and being an empty state. A procurement decision the console is meant to inform, but which also gates the console.

09

Does anyone know what removed the Unsaved/ data?

Not blocking — the derivations are all recoverable — but worth five minutes with Ahsan. There is no lifecycle rule on that bucket, so something or someone deleted it, and if that mechanism is still running it will do the same to the next set of tables.

10

Are dev and prod separate, or is there one environment?

Cheap to decide now, expensive later — it is baked into every bucket name and stack parameter.
